# 劇組流程：像設計師一樣先對方向，再修細節

一個 Claude 從頭做到尾，會自己提案、自己做、自己審，粗糙的地方沒人擋；但劇組如果一開始就逐格挑像素，故事反而沒人管。這份把工作拆給 subagent，並照設計師的順序走：

**參考 → 故事因果 → 視覺隱喻 → 做一版 → 方向審查 → 給使用者看 →（重複）→ 使用者說 OK → 精修審查 → 匯出**

主流程只負責派工、跑腳本、整合，**不自己打分**；agent 回報的結果主流程要自己重跑腳本或看圖驗證，不直接採信。

```
主流程（你）：問參考與素材 → 寫 brief.md、source.txt、story.md → 派工 → 每版給使用者看 → 匯出
  │
  ├─ 導演 ×3（平行）  各提一種「故事＋視覺隱喻」→ 讀另外兩案互評、投票
  ├─ 製作 ×1–2       依定案做一版（美術共用畫筆／動畫場景，兩人不碰同一檔）
  ├─ 審查 ×3（平行）  每輪全新 subagent。第一階段：故事因果、視覺隱喻、視覺傳達、素材忠實度
  │                  第二階段（使用者 OK 後）：rubric 的一票否決與七個維度
  └─ 反審查 ×1       每輪全新 subagent，檢查審查回報有沒有被汙染、放水或互抄
```

導演與審查都用 Agent 工具派工（平行的在同一則訊息一起派）；導演在後續輪次用 SendMessage 接續同一個 agent（它記得自己的案）；製作也用同一個 agent 接續每一版（它記得程式）。

**審查一律用全新的 subagent**：每一輪、每一位審查都重新用 Agent 工具派，不用 SendMessage 接續，也不由主流程、導演或製作兼任。同一個 session 做過、看過的東西會帶著盲點和偏好，換一個沒看過製作過程的 agent 才看得出問題。審查只拿到成品與檔案（縮圖、HTML、`brief.md`、`source.txt`、`story.md`／`spec.md`、`rubric.md`），不給製作過程的對話、不給上一輪的分數；三位審查各自獨立交件，交件前看不到彼此的評分。

## 0. 主流程準備（開工前問使用者，只問這些）

1. **素材**：文件、網址、口述內容 → `source.txt`。畫面上與旁白裡的每個事實都只能從這裡來。
2. **參考風格**：「有沒有想要的片子、廣告或畫面當參考？」抽象詞（科技感、發表會、高級感）不夠，要具體作品或畫面。使用者沒有就由導演各提一種，給使用者看縮圖選。
3. **要不要人物、要不要旁白／字幕**、平台與比例、片長上限。
4. **禁區**：使用者說過不要的方向。
5. **品質標竿**（不主動問）：使用者有說「用好萊塢標準」「Pixar 等級」「募資等級」這類話就照做（七個標竿見 `rubric.md`），沒說就是 Apple 發表會。標竿只定義好到什麼程度，不規定做法（見 `rubric.md`「品質標竿」）。

寫成 `brief.md`。接著主流程把素材的幾個發現寫成一條**因果故事線** `story.md`（例：鉤子 → 但 → 於是 → 意義），連接詞可以加，事實不能加。

## 1. 導演：故事＋視覺隱喻（3 人，平行，再互評）

每位導演從不同的視覺語言出發（例：字體動態／抽象光點／介面系統／具體物件隱喻），各寫一份 40 行內的處理：每一拍的主畫面、哪個物件從上一拍延續、轉折那一拍怎麼讓人一眼看懂、數字放在哪。**不寫像素與緩動細節，不做原型。**

導演提案時不要為了「像標竿」而套它的招牌手法；標竿是觀眾看完的反應，用什麼畫面達到由導演自由發想。

唯一的評判標準：**靜音、手機縮小、不讀任何字，觀眾能不能從畫面說出故事？** 純文字、數字卡排排站的案直接不及格——要用畫面「演」（物件在做事、狀態在改變），不是用字「寫」。

交件後用 SendMessage 請每位導演讀另外兩案、互評、投票（可投自己），並各提一個要從別案借的元素。多數票的案為本，合併被兩人以上提到的借用元素，主流程寫成正式規格（`spec.md`）。

## 2. 製作（1–2 人）

依 `spec.md` 做一版，跑 `verify.py`（canvas-motion 專案）或自己的截圖腳本，交縮圖總覽。兩人分工時，美術負責角色／共用畫筆／錨點，動畫負責各幕，**不碰同一個檔案**。這一階段**不要花時間在像素對齊**。

## 3. 方向審查（3 人，平行）——每一版都做

審查只看 `rubric.md` 第一階段的四項：故事因果、視覺隱喻、視覺傳達、素材忠實度。看縮圖總覽、`storyboard.json`／`spec.md`、`source.txt`、`brief.md`；每人最多 5 條修改，只談故事與畫面。事實錯誤（素材沒有的數字或推論、動畫過程中出現的中間數字、旁白與原文用詞不符）一律擋下。

**審查通過、而且反審查判定有效，就給使用者看**（HTML＋縮圖）。使用者的方向回饋優先於審查分數：他說「都是文字」「要更像」「要科技感」時，回到第 1 步或第 2 步改，不要繼續在細節上打轉。使用者說要提早看，就直接給當下的版本。

## 3.5 反審查（1 人）——每一輪審查之後都做

審查本身也可能出錯，所以三位審查交件後，再派**一位全新的反審查 subagent** 檢查審查有沒有被汙染。它沒看過製作過程，也沒參與審查，只拿到三份審查回報、成品縮圖與 HTML、`brief.md`、`source.txt`、`rubric.md`。

逐份檢查：
- **被製作過程帶著走**：回報裡引用了只有製作對話才知道的理由、替製作者的取捨辯護，或沿用 `spec.md` 的說法而不是看畫面。
- **沒有證據的分數**：給分或扣分沒指出秒數、縮圖格與具體改法；「整體不錯」「不夠精緻」這類空話。
- **放水**：全部 ≥ 8 卻幾乎沒有 fixes，或明顯的問題（疊字、脫開、事實錯誤）沒被抓到。反審查自己抽看縮圖、對 `source.txt` 抽查數字。
- **用風格扣分**：以「不像代表作」「不像 iPhone 發表會」扣分，而不是以觀眾反應沒到扣分；或因為打破慣例被扣分。
- **三份互相抄**：三位的分數、用詞、fixes 高度一致，像是看過彼此或共用同一份上下文。
- **越權**：方向審查在挑像素，或精修審查在改故事方向。

回傳每份審查的判定：`有效`、`部分無效`（列出哪幾條作廢）、`無效`。被判無效的審查，重新派一位全新的審查 subagent 補做；作廢的條目不進修改清單。反審查只判斷審查是否可信，**不自己打分、不提新的修改**。主流程照樣自己抽看縮圖驗證，不直接採信反審查。

## 4. 精修審查（使用者說 OK、要匯出前才做）

同樣派三位全新的審查 subagent，不沿用方向審查的那三位；交件後同樣做反審查（3.5 節）。

這時才用 `rubric.md` 第二階段（一票否決＋七個維度，每項 ≥ 8）逐格檢查：連線脫開、文字溢出、殘影瞬移、字級太小、留白對齊……修一到兩輪後匯出。

## 5. 交付

正式匯出後主流程自己用 view 看抽格。交付說明附：故事線一句話、採用了誰的案與借用元素、使用者做過的取捨（例如拿掉某句）、沒能驗證的部分（例如沒實際聽過有聲播放）。

## 人數

預設 3 導演＋1–2 製作＋3 審查＋1 反審查。導演與製作跨版本接續使用；審查每一輪都換全新的 subagent。片長 15 秒內、素材少時可縮成 2 導演＋1 製作＋2 審查，但**審查一定和製作分開**。

# 十人劇組：提案、評選、製作、審查

一個 Claude 從頭做到尾，會自己提案、自己做、自己審，粗糙的地方沒人擋。這份把工作拆給 **10 個 subagent**，主流程只負責派工、跑腳本、整合，**不自己打分、不自己判定「這樣可以」**。

提案和評選都在 agent 之間進行，**不給使用者看**。使用者只提供需求與素材、收成品。

```
主流程（你）：讀需求 → 寫 brief.md、source.txt → 派工 → 跑 verify／export → 彙整 → 交付
  │
  ├─ 提案  ×3  導演 A／B／C（平行）      各自提一個方向，畫出高光原型縮圖
  ├─ 評選  ×2  評審甲／乙（平行）        用 rubric 給三案打分，選一案或合併
  ├─ 製作  ×2  美術（先）→ 動畫（後）     美術定角色、配色、共用畫筆；動畫寫每一幕
  └─ 審查  ×3  動態、美術細節、素材（平行） 看縮圖與抽格打分，不達標就退回製作
               └ 最多 3 輪；每一輪都派新的審查 agent（不沿用上一輪的對話）
```

主流程用 Agent 工具派工（`subagent_type: "general-purpose"`），平行的角色在同一則訊息一起派。每個 agent 的 prompt 都要帶：專案絕對路徑、skill 路徑、要讀的文件、負責的檔案、交出什麼。agent 回報的結果主流程要自己重跑腳本驗證，不直接採信。

## 0. 主流程準備

在專案資料夾建立：
- `brief.md`：目的、觀眾、平台、比例、片長上限、核心訊息、**不能碰的方向**（使用者說過不要的）、使用者的偏好。
- `source.txt`：素材原文。畫面上的每個字都只能從這裡來。

## 1. 提案：導演 A／B／C（3 人，平行）

每位導演在 `proposals/<A|B|C>/` 獨立工作，**看不到彼此的提案**。給每位導演不同的起點，避免三案長得一樣：
- A：最直接、最好懂的隱喻
- B：換一個視角或尺度（從物件的角度看、從一個點拉到整座城市）
- C：換一種結構或媒材（倒敘、一鏡到底、角色故事）

每位導演要交：
1. `proposals/X/storyboard.json`：完整分鏡（`say`、`hero`、`carry`、`sfx`，人物寫 `cast`）。先跑 `storyboard.py --preview`，不能有 ✗。
2. `proposals/X/concept.md`：一段話說明隱喻與為什麼適合這個素材，每幕的高光畫面。
3. **高光原型**：用 `storyboard.py storyboard.json proposals/X` 產生專案，只把**最關鍵的一幕**寫完整（人物用 Open Peeps），其他幕留鷹架；跑 `sheet.py proposals/X --aspects <交付比例> --at <高光秒數前後三個時間點>`，交出縮圖路徑。

必讀：`SKILL.md`、`direction.md`、`craft.md`、`character.md`、`rubric.md`、`brief.md`。

## 2. 評選：評審甲／乙（2 人，平行）

各自獨立讀三份 `concept.md`、`storyboard.json`、用 view 看三份高光原型縮圖，依 `rubric.md` 打分（原型只評得到的維度：構圖、角色與素材、素材忠實度，加上「隱喻是否新鮮、是否一眼看懂」）。

每位評審交：
```json
{ "ranking": ["B", "A", "C"], "scores": { "A": 7.6, "B": 8.4, "C": 7.1 },
  "pick": "B", "graft": ["A 第 3 幕的流程圖收束比 B 好，換進 B"], "must_fix": ["B 第 2 幕主角太小"] }
```

主流程裁決：兩位的 `pick` 相同就用它；不同就取兩人平均分最高的一案。`graft` 與 `must_fix` 兩人都有提到的一定採用，只有一人提到的由主流程依 rubric 判斷。結果寫成正式的 `storyboard.json` 與 `decision.md`（選了哪案、合併了什麼、為什麼）。

## 3. 製作：美術 → 動畫（2 人，依序）

兩人不碰同一個檔案。

**美術**（先做）負責：
- `project.json` 的 `style`、`cast`、`anchors`；
- `scenes/00_common.js`：角色設定、共用畫筆（例如 Agent 方塊、流程節點）、跨幕位置函式。
- 用 view 看 `references/peeps/` 型錄挑部件；跑 `castsheet.py` 交角色設定表。
- 交付前跑 `build.py`，不能有 ✗。

**動畫**（美術完成後）負責 `scenes/01_*.js` 之後的每一幕。必讀 `api.md`、`craft.md`、`motion-design.md`、`rubric.md`、`decision.md`，可以呼叫但不能改 `00_common.js`（要改就回報主流程轉給美術）。跑 `verify.py <專案> --aspects <交付比例>` 到結束碼 0。taste 提醒不能自己判定「刻意」：真的要保留，在 storyboard 該幕寫 `intent`，交審查判斷。

## 4. 審查：動態、美術細節、素材（3 人，平行）

主流程先準備審查材料，**審查 agent 不看程式碼**：
- `verify.py` 的縮圖（`sheets/sheet_*.jpg`）與 `motion.png`；
- 每幕高光前後 ±1 拍的密集抽格：`sheet.py <專案> --aspects <比例> --at <每 1/6 秒一格>`；
- 匯出預覽 `export.py <專案> review.mp4 --preview --verify <每幕高光秒數>` 的抽格；
- `storyboard.json`、`source.txt`、`brief.md`、taste 的 intent 清單。

| 審查 | 負責維度 | 特別看 |
|---|---|---|
| 動態導演 | 動作質感、節奏與聲音 | 高光是不是整幕最有力的一瞬、動作有沒有預備與餘波、有沒有亂抖或殘影；逐條判斷 intent 是否成立 |
| 美術細節 | 構圖與留白、字級與文字層次、角色與素材、細節精度 | 逐格看密集抽格：連線、陰影、標籤是否跟著主體；人物是否 Open Peeps；對齊與留白 |
| 素材忠實度 | 素材忠實度 | 每個數字、用字對照 `source.txt`；限制說明是否在數字旁；有沒有 brief 裡說不要的方向 |

回報格式見 `rubric.md`「審查回報格式」。

## 5. 修改迴圈（最多 3 輪）

1. 主流程彙整三份回報：任一維度 < 8、平均 < 8.5、或有一票否決 → 不通過。
2. 把 `fixes` 依檔案分給美術或動畫（同一個 agent 繼續修，用 SendMessage 接續它的對話），修完重跑 `verify.py`。
3. **派新的三位審查**重新評（不給它們上一輪的分數，避免錨定），但附上一輪的 `fixes` 清單，讓它們確認有沒有修好。
4. 第 3 輪仍未通過：交付當下最好的版本，並在交付說明列出未達標的維度、分數與原因，不宣稱已達標。

## 6. 交付

通過後主流程才跑正式匯出（`export.py … --blur 5 --verify …`），自己用 view 看抽格一次，然後交付。交付說明附：選了哪一案與原因（一句話）、最後一輪三位審查的分數、以 intent 保留的提醒與審查的判定。

## 人數與成本

10 個角色是上限也是預設：3 導演＋2 評審＋2 製作＋3 審查。片長 15 秒內、素材很少時可以縮成 2 導演、1 評審、1 製作、2 審查，但**審查一定和製作分開**。修改迴圈裡新派的審查算在原本 3 個審查席位內。
